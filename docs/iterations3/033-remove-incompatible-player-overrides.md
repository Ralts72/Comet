# 033 逐条处理失效的个人输入覆盖

## 背景与前后对比

项目默认设置允许删除动作和绑定，个人文件按稳定 UUID 保留旧意图，这个边界没有问题。
但玩家面板只枚举仍存在的默认动作和绑定，失效记录只出现在诊断文字中：

- 删除默认动作后，只能“全部恢复默认”，连其他动作的有效改键一起删除。
- 删除默认绑定后，至少要恢复整个动作，连这个动作其他绑定的个人配置一起删除。

本项把路线图的“不兼容记录可显式修复”补成可操作的界面，不自动清理文件。

## 代码变化

原 `render_diagnostics()` 仅画消息与 UUID，现在每条 Issue 后提供“移除此覆盖”：

```cpp
if(issue.binding)
    restore_binding(issue.action, issue.binding);
else
    restore_action(issue.action);
```

Issue 已有足够的结构信息，不匹配英文错误字符串，不增加枚举、引擎 API 或新 owner。
控件以动作／绑定 UUID 两层作用域形成稳定身份，翻译不会改动操作目标。
遍历的是 resolve 结果，不是被修改的草稿容器；移除后下一帧重新合成诊断。

动作错误只产生动作级 Issue，绑定错误使用绑定级 Issue。删除一个绑定覆盖后，
既有 `restore_binding()` 负责清理未禁用且没有其他覆盖的空动作记录。
其他记录包括未操作的失效记录都原样保留。

## 生命周期与架构价值

这是原玩家面板的一个草稿命令，不是新的文件修复服务：

```text
诊断 → 按身份删除草稿记录 → Apply → 原文件保存 → 原 Runtime 更新边界
                         └→ Cancel → 丢弃草稿
```

全部默认动作都已删除时，诊断仍独立显示并可处理。禁用动作内部没有参与合成的子绑定，
继续在动作启用后才给出兼容性诊断，不额外扫描和主动洗掉它们。
没有修改文件版本、存储策略、运行时合成或输入授权。

## 限制与后续

该按钮仅移除已诊断的覆盖，不是任意编辑不存在的动作。损坏 JSON 仍走加载错误，不把解析失败文件当空文件覆盖。
真实宿主人工改键闭环限制沿用 031；本项的 UI 和持久化用例不冒充桌面手工验收。

# 032 禁用玩家绑定时保留个人配置

## 背景

之前把旋转从 Space 改成 K，再勾选“禁用绑定”，会把覆盖替换成只含 disabled 的记录。
取消禁用又删除记录，结果变回 Space。动作级禁用同样会清掉下面所有调参。
这符合旧文件的互斥设计，却不符合一个可反复切换的启停开关。

本项对应路线图“玩家覆盖独立保存”：禁用、重新启用和恢复默认有明确区别。

## 前后代码变化

之前禁用和字段不能同时存在：

```cpp
if(binding.disabled ? has_fields : !has_fields)
    return failure(...);
```

现在只拒绝既未禁用、也没有任何覆盖的空记录：

```cpp
if(!binding.disabled && !has_fields)
    return failure(...);
```

动作层遵循同一规则。禁用不会绕过 UUID、重复身份、控制枚举、有限数值和容量校验；
倍率／死区是否兼容当前默认控制，仍由 resolve 负责。

```cpp
auto patch = binding_patch(action.id, binding.id);
patch.disabled = disabled;
commit_binding(action, binding, std::move(patch));
```

面板的字段编辑继续先验证合成绑定；启停则只提交结构合法的原记录。
否则一个因项目默认来源变化而失配的旧死区，会让用户连禁用开关都无法操作。
重新启用后由同一 resolve 给出有效默认与诊断，不把失配字段清掉。

恢复绑定／动作／全部仍删除对应覆盖。纯 disabled 记录没有其他个人字段，重新启用时移除，
继续继承今后的项目默认值。动作类型漂移仍须先恢复动作，不让一个失效标记冒充真正禁用。

## 持久化与显示

序列化原先使用 disabled 与字段的 if/else，现在分别写出，两者可以共存：

```json
{"id":"<binding UUID>","disabled":true,"source":"key","control":"K"}
```

玩家文件版本升为 v2。按项目现有策略，v1 明确报错且不改写；不添加兼容解析、迁移工具或备份文件。
旧版本已经丢掉的个人键位不能推测恢复。Project 的 v2 格式不受影响。

禁用内容不再展示默认 Space 冒充个人 K；显示“已禁用；个人配置仍保留，重新启用后恢复”。
数据只有 InputOverrides 一份，UI 不维护影子副本或恢复缓存。

## 架构价值

- 启停属于输入覆盖的数据语义，不是面板的特殊补丁；文件重开与 App／Play 使用同一结果。
- 结构校验、默认值相关校验、字段编辑和启停各守边界，没有新增类、文件协议 owner 或回调。
- 原 resolve 的身份／类型检查与禁用优先顺序足够，不增加另一套禁用合成路径。

## 限制与后续

不增加个人动作、组合键、多人设备或自动文件重载。禁用动作时保留的子绑定只在动作重新启用后参与合成。
桌面自动点击的指针回读限制见 031；本项不把自动 UI 回归当作真实 App／Play 手工改键验收。
